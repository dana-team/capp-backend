# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
make build           # Build server binary → bin/server
make run             # Run locally with default config (config/config.yaml)
make test            # Unit tests with race detection (go test -v -race ./...)
make test-cover      # Generate HTML coverage report
make lint            # golangci-lint
make fmt             # gofmt
make vet             # go vet
make tidy            # go mod tidy (CI fails when it produces a diff)
make docker-build    # Build Docker image
make build-cli       # Build cappctl CLI binary → bin/cappctl
make build-capp-mcp  # Build capp-mcp binary → bin/capp-mcp
make run-capp-mcp    # Run capp-mcp against a local backend on :8080
make fetch-ui        # Re-download the embedded Scalar bundle (internal/server/ui/scalar.min.js)

go test -race -run TestConvertCoverage ./internal/resources/namespaced/capps/   # single test
```

`make build`/`run`/`build-cli`/`build-capp-mcp` run `fmt` and `vet` first. CI is split by path into three workflows: `test.yaml` (server; vets, lints and tests everything **except** `internal/cli`, `cmd/cappctl`, `internal/mcpserver`, `cmd/mcp`, plus `helm lint` and a `go mod tidy` diff check), `test-cli.yaml` (`./internal/cli/... ./cmd/cappctl/...`, also cross-builds Windows), and `test-capp-mcp.yaml` (`./internal/mcpserver/... ./cmd/mcp/...`). `make test` runs all of them locally. In each workflow the lint/test job and the build job run in parallel; the build job compiles the binary on the runner and packages it with the Dockerfile's `prebuilt` stage (`--build-arg BINARY=prebuilt`, copies `dist/<binary>`), and the release Docker jobs do the same. Go caching goes through `.github/actions/setup-go`, which keys the module + build cache per job (`cache-key`); do not switch back to setup-go's `cache: true`, whose single go.sum key makes jobs overwrite each other's build cache. Don't add `type=gha,mode=max` BuildKit caches for the Go images: their layers filled the 10 GB repo cache and evicted the Go caches. Local `docker build` (default `BINARY=builder`) compiles from source with BuildKit cache mounts. Every server build (`make build`/`run`, `deploy/Dockerfile`, the build steps in `test.yaml` and `release.yaml`) passes `-tags=nomsgpack,grpcnotrace` to drop gin's MessagePack codec and grpc's `x/net/trace` import (binary about 8% smaller); a new place that builds `cmd/server` needs the same tags. Tests, vet and lint run without them.

## Contribution Workflow

- **Commits and PR titles** use Conventional Commits with a scope: `feat(capps): ...`, `fix(authorization): ...`, `test(auth): ...`, `build(deps): ...`, `ci: ...`. Scopes in use: `capps`, `cappctl`, `mcp`, `namespaces`, `authorization`, `auth`, `cfunc`, `docs`, `helm`, `deps`. A PR is one squashed commit whose subject equals the PR title; review fixes are amended into it, not stacked as extra commits.
- **Merging** is done by Prow (`dana-prow-ci`): it needs an LGTM review plus approval from an `OWNERS` approver, then merges by itself. Releases are cut by pushing a `v*.*.*` tag (`release.yaml`).
- **A feature PR carries its own docs.** A route or DTO change updates `api/openapi.yaml` and this file in the same PR; a config change updates `config/config.yaml`, `helm/capp-backend/values.yaml` and the chart templates; a route agents should reach adds a `capp-mcp` tool; a user-facing CLI change updates `docs/cappctl.md`.
- **PR body** follows `## Summary` (or `## Why` / `## What` / `## How` for a larger change) → `## Breaking config changes` (a table of Helm values, only when needed) → `## Review focus` (the one decision the reviewer should check) → `## Testing`. The Testing section names the commands run (`make lint`, `TZ=UTC go test ./...`) and states plainly what was **not** verified (for example "not run against a real operator").
- **Large features are split into a stack** of small PRs, one layer each, in the order: dependency bump → API types/DTOs → endpoints → safety fixes → cappctl → capp-mcp. Each body ends with a `## Stack` list ("Part 3 of 6. Merge in order."). CI runs only on PRs that target `main`, so the upper parts of a stack must be verified locally.
- **Review comments** here are about behavior under failure and retry (a partial failure followed by a repeated request, two writes in the same second, a CI path filter that misses a moved package), not style. Answer each with the fixing commit and the new behavior.

## Architecture

Multi-cluster API gateway for Capp resources, built with **Go + Gin**.

### Request Flow
```
Request → Recovery → Logging → Metrics → CORS → ClientVersion → RateLimit → Auth → ClusterResolution → ResourceHandler
```

The flow below describes Kubernetes authorization mode (the default).

1. **Auth middleware** validates the token (mode-dependent) and attaches a credential to context
2. **Cluster middleware** resolves `:cluster` param, checks health, builds a per-request scoped K8s client with the user's credential, validates namespace against allowed list. It also sets an admin client (`AdminK8sClientKey`, the cluster's own SA credential with no impersonation) for discovery-style listing such as namespaces. Context keys live in `internal/middleware/keys.go`.
3. **Resource handler** performs the CRUD operation using the scoped client

Handler tests use `internal/testutil` (fake controller-runtime clients with SAR allow/deny variants, `EngineHelper` for HTTP calls, and mock Auth/Cluster managers) instead of real clusters.

Backend-policy mode (LDAP, OpenShift or passthrough) installs a global chain from `internal/middleware/policy`: classify the registered method/route, authenticate nonpublic requests, authorize the operation/target, then prepare execution. It does not run Kubernetes-mode Auth/Cluster groups or install a generic admin client. Ordinary operations receive a namespace-bound execution client; aggregate/migration paths authorize each namespace separately. Missing authorization context must deny rather than fall back.

`internal/authorization` owns strict assignments, per-cluster namespace/policy observations and metadata-only UID association. `internal/server/authorization.go` owns startup/readiness/shutdown; HTTP work drains before workers stop. The namespace handler's narrow administration component owns system-client policy/quota/lifecycle access. Operator users OR groups authorize administration without granting ordinary resource access. See [backend-policy operations](docs/backend-policy.md) for contracts and recovery; implementation does not establish a shipped release or deployment validation.

Use the `gin-openapi-sync` skill to regenerate it when you have it (it is a user-level skill, not part of this repo); otherwise edit the spec by hand. ### Key Patterns

**ResourceHandler interface** (`internal/resources/registry.go`): Pluggable handlers register routes and are enabled/disabled via config. Current handlers: `capps`, `capprevisions`, `namespaces`, `configmaps`, `secrets`, `cfuncpools`, `cfuncfunctions`. To add a new resource type, implement the interface, register it in `cmd/server/main.go`, and add its name to the `enabledResources` map there (plus a `ResourcesConfig` field and default in `internal/config/config.go`). The registry skips only names explicitly set to `false`; a handler missing from the map is always mounted. A new route also needs a rule in `internal/middleware/policy/routes.go` (an unlisted route is denied in backend-policy mode; `TestNewPolicyRouteCoverage` fails on one) and RBAC in both `helm/capp-backend/templates/capp-user-cr.yaml` (Kubernetes mode) and `clusterrole.yaml` (backend-policy mode).

**cfunc pools** (`internal/resources/namespaced/cfunc/pools`, `resources.cfunc` config, DTOs in `pkg/api/cfunc`): cfunc is function as a service on Fission. A pool is a set of warm pods of one language runtime, stored as a `fission.io/v1` Environment; the API calls it a pool and sets no labels or annotations on it. The package follows the capps layout: `types.go` (route list + DTO aliases), `convert.go` with the pure `ToK8s(req, existing, namespace, catalog)` / `FromK8s(env, catalog)` pair, `handler.go`, and `drift_test.go`, whose `TestConvertCoverage` fails when a new `PoolRequest` field is not populated in `fullPoolRequest()` and round-tripped. One `PoolRequest` serves `POST` and `PUT`; on `PUT` the URL name is authoritative. `catalog.go` resolves the config once in `New` (parsed resources per size, the largest limit of any size, runtime image → flavor), so nothing is re-parsed per request or per listed pool; `New` returns an error for that reason. A client sends `flavor` and `size`, never an image. `ToK8s` writes what the config holds behind them: the flavor's runtime image, build image, build command, `builderEnv` (onto `spec.builder.container.env` only) and `keepArchive`, the shared `imagePullSecret`, and the size's resources. The optional `env` list (the shared `EnvVar` DTO, with `value` or `valueFrom`) goes onto `spec.runtime.container.env` only, in a container named after the Environment as Fission expects; the update handler sets `req.Name` from the URL before `ToK8s` for that reason, because a container named after the body would make Fission rename the pod's main container. `env` is full replace on `PUT` through `containerspec.MergeEnvVars`. The optional `advanced` block overrides `resources` and, only when `resources.cfunc.allowCustomBuild` is true, `buildImage` (a full image reference, no prefix) and `buildCommand`; that switch is off by default because a caller who can create a pool could otherwise make the Fission builder run any image and command. `advanced.resources` is laid over the size: a value it leaves out comes from the size, because a block with one request would otherwise produce a pod with no limits, and the merged result is capped at the largest configured size. `poolSize` is capped at `resources.cfunc.maxPoolSize`. `FromK8s` returns an `advanced` block whenever the stored resources or build settings differ from the flavor and size, so that a response sent back in a full-replace `PUT` keeps them; `TestConvertCoverage` asserts that round trip. `PUT` is full replace for the request fields; `ToK8s` copies the existing spec first, so pod specs and a non-zero grace period survive, and a stored grace period of 0 is replaced with 360. The update handler answers 409 for an Environment below version 3 (only possible when it was created outside the API), because the version is immutable and the pool size has no effect there. Nothing records the flavor or size: `FromK8s` derives them by matching `spec.runtime.image` and `spec.resources` against the config, which is why validation rejects two flavors with one image and two sizes with equal quantities, and why both read empty for a foreign Environment or after the config moves a flavor to a new tag (the next `PUT` re-applies the config). Three Fission v1.27.0 behaviours are load-bearing, and the `fission` CLI hides all three by always sending a value: `spec.version` is always 3 because `poolsize` is ignored below it; `terminationGracePeriod` is always written (360) because an omitted value is stored as 0 and pods are then killed with no drain window; and `spec.builder.command` is written as `build` whenever there is a build image and no command, because the Fission builder otherwise runs `/build`, which the official build images do not have, and every source build fails. A flavor image must speak the v2 interface (`/v2/specialize`); a v1-only image such as `perl-env` starts warm pods but cannot load a function. `builderEnv` is a list, not a map, because Viper lowercases map keys; flavor and size names are lowercase for the same reason. The in-use check on `DELETE` lists the Functions of the pool's own namespace only; Fission's admission webhook refuses a Function that names an Environment of another namespace, so the check is complete only where that webhook runs. A cluster without the Fission CRDs returns 501 through the `meta.IsNoMatchError` case in `apierrors.translateK8sError`. cappctl and capp-mcp do not cover cfunc yet.

**cfunc functions** (`internal/resources/namespaced/cfunc/functions`, `internal/cfuncsource`, `resources.cfunc.functions` config): a function is code from a git repository plus its triggers, exposed as one object. Fission has no such object, so one function is a `Function`, a `Package` of the same name, and one `HTTPTrigger` or `TimeTrigger` named `<function>-<trigger>` for each entry of `triggers`. `convert.go` has `Validate` (everything that needs neither the cluster nor git, so a bad request is refused before either is contacted), `ToK8s(req, existing *Objects, namespace, pool, code, settings)` and `FromK8s(objects, routerURL, settings)`; `drift_test.go` also asserts that a response sent back as a request gives the same objects. The handler order is validate → read the pool → clone → write package → write function → reconcile triggers, and every step reads state first so a repeated request finishes a failed one: a create that failed before the function was saved adopts the leftover package, a failure after it answers `apierrors.NewPartialFailure` ("function X is saved, but…") and the same body in a `PUT` completes it, and `delete` removes the function last. Load-bearing details: (1) the executor is always `poolmgr` and `InvokeStrategy.StrategyType` is always written, because the Fission CRD requires it; a function on another executor answers 409 on `PUT`. (2) The pool must be in the function's namespace (Fission's webhook refuses anything else) and at interface version 3. (3) Every http path is written as `/<namespace>/<function><path>`, because the Fission router has one cluster-wide URL space, also with its tenancy feature. (4) `cfuncsource.Fetcher` clones in memory with the configured token and refuses a `source.url` outside `git.baseURL` (host and path-segment match), since the token is sent to whatever host is cloned; its errors are `InputError` (400) or anything else (502 `CFUNC_SOURCE_FAILED`, cause not shown). The archive is deterministic (sorted entries, fixed time), so an unchanged commit is byte-identical and starts no build. (5) Code goes inline as a literal archive, at most `fissionv1.ArchiveLiteralSizeLimit` (256 KiB): `source.build` decides where it goes (default: a folder in a pool with a build image is built, one file is not): built code is `spec.source` and Fission builds it, other code is `spec.deployment` (one file is stored as that file, as `fission fn create --code` does). A package that changes from built to not built gets its build state set to `none`, because Fission loads a package only when the state is `succeeded` or `none`. The archive keeps git's executable bit, or a `build.sh` build command fails with "permission denied". The writes that follow the package create or update (owner reference, build state, build-request annotation) are merge patches, because Fission's builder writes to the same package at the same time and an update conflicts with it; the kind test hit that conflict. (6) Fission builds a new package by itself but rebuilds an existing one only when `status.buildstatus` is set to `pending` through the status subresource, a second write after the code; `BuildRequestAnnotation` (a hash of source, build command and pool) is written last, so a `PUT` repeated after a failure between the two still requests the build. (7) Fission has no field for the git source, so the package carries it in `cfunc.dana.io/source-*` annotations. (8) Triggers belong to a function by `functionref.name`, not by owner reference, so triggers made with the `fission` CLI are shown and replaced too; owner references are set as well, only so that a function deleted with kubectl takes its objects along. A wanted trigger name that is taken by an object of another function is a 409. (9) `secretVolumes`/`configMapVolumes` reuse the Capp DTOs from `pkg/api/common`, but Fission fixes the mount path (`/secrets/<ns>/<name>`, `/configs/<ns>/<name>`), so `name` and `mountPath` are response-filled and a request may only repeat them. (10) A cron schedule is parsed with the same parser options as Fission's timer and refused when two of its next 120 runs are closer than `minCronIntervalSeconds`. (11) `concurrency` defaults to `defaultConcurrency`, which is Fission's own 500 on purpose: an earlier default of 5 answered 429 after six quick calls on kind, because Fission v1.27.0 with `tenancy.mode=dynamic` does not reuse a function's pod in a namespace onboarded at runtime (the executor's `IsValid` reads the pod through a cache scoped to the namespaces known at start), so every request takes a new pod until the idle reaper runs. The test route calls only `cfuncRouterURL` + a path of the function's own trigger and does not follow redirects (Fission's internal `/fission-function/...` path needs a signature the backend cannot make). The logs route needs pod logs, which the controller-runtime client cannot read: the cluster middleware puts a `cluster.PodLogs` function, bound to the caller's credential, under `middleware.PodLogsKey`; backend-policy mode does not, and the route is `Denied` there. `secrets` and `configmaps` hold a `boundcapps.FunctionGuard`, turned on with `WithFunctionGuard(true)` when functions are on: delete is then also refused while a function reads the object, and `/bound` returns `boundFunctions`. `FindFunctions` treats a 403 on the Function list like a missing CRD, so a Role that grants Secrets but nothing of Fission keeps working. `resources.cfunc.onboardNamespaces` makes pool create label the namespace `fission.io/enabled=true` (Fission `tenancy.mode=dynamic`), with the caller's client first and the admin client on a 403, but the admin client is used only after a SelfSubjectAccessReview shows that the caller may create Environments there; otherwise a caller with no right in the namespace would get it labelled for good before its create is refused. More rules that came out of review: the 256 KiB limit is checked in `ToK8s` on the literal that is stored (zip when built, the file when one file is not), not in the fetcher; `cfuncsource` holds at most `maxConcurrentFetches` clones in memory, because a clone is read in full before any size limit applies; `create`, `update` and `test` call `extendWriteDeadline`, because a clone (60 s) or a function call outlasts `server.writeTimeoutSeconds` and the client would get a closed connection while the handler still writes to the cluster; a package is adopted, replaced or deleted only when it carries the `cfunc.dana.io/source-url` annotation (`managedPackage`); anything else of that name is a 409 on create and update and is left alone on delete, and `update` looks the function-named package up also when the package the Function references is missing; `create` loads the triggers that already name the function (orphans of a delete, or CLI-made) and replaces them like an update; `uniqueTriggerNames` keeps API trigger names unique in a response when a foreign `x` meets a managed `<function>-x` or two kinds share an object name; HTTPTriggers and TimeTriggers go through the same generic helpers (`findByName`, `triggersOf`, `reconcileTriggers`), so change trigger logic once; lists run together (`listTogether`, `namespaced.ListAllTogether`, `policy.ListAggregates`) and the logs route reads the Function only; a failed build is requested again on `PUT` even for the same code; the function's `packageref.resourceversion` is what tells Fission's executor to drop the function's pods and load the package again (the executor reacts to a generation change only, so metadata writes are free), and `pointAtCode` decides who moves it: for code that is NOT built this API moves it, only when the Function is behind the code, which it reads from the Function's `cfunc.dana.io/code` annotation (`codeHash` of the package) and does not remember from the request, so an unchanged `PUT` writes nothing and a `PUT` repeated after the package write succeeded and the Function write failed still repoints; for code that IS built this API never moves it on `PUT`, because the fetcher refuses a package whose build is pending and Fission's builder moves it when the build succeeds. That does NOT keep the last good build serving through a failed build (measured on kind, v1.27.0): the builder writes the result to the Function's status, the executor keys pods on the Function's resourceVersion (`crd.CacheKeyURG`) and drops them, and a new pod cannot fetch a failed package, so the function answers 500 until a build succeeds; only a package for each build would change that, and the backend has no controller to repoint after a build; `Validate` refuses two http triggers on one method and path; the logs route returns a pod whose log read answers 404 or 400 with no lines, which is normal while Fission recycles pods; a fetch that gets no slot is `cfuncsource.ErrBusy` → 503 `CFUNC_SOURCE_BUSY`, not a git server failure, and the slot bounds the number of clones, not their size. The handler patches Packages and `packages/status`, so both RBAC templates need the `patch` verb on them; the fake client does not enforce RBAC, so only a cluster shows a missing verb.

**capp-mcp** (`cmd/mcp/`, `internal/mcpserver/`, `helm/capp-mcp/`): A separate binary that exposes the REST API as MCP tools over Streamable HTTP (`POST /mcp`, `GET /healthz`; flags `--port`/`CAPP_MCP_PORT` 8081, `--backend-url`/`CAPP_BACKEND_URL`, `--insecure`). It holds no credentials: `AuthMiddleware` puts the client's bearer token in the request context, and each tool calls capp-backend through the cappctl HTTP client (`internal/cli/client`) using that token, so backend RBAC still applies. Tools are grouped into `ToolSet`s (`tools_*.go`) registered in `server.go`: clusters, namespaces, capps, capprevisions, configmaps, secrets (read-only, metadata only); configmaps and secrets each have a `*_bound` tool for the `/bound` route. A new backend route that agents should reach needs a matching tool here.

**Client version check** (`pkg/clientversion`, `internal/middleware/clientversion.go`): The server and cappctl both take their version from `-X main.version=<tag>` (release workflow `go build` ldflags; source builds of `deploy/Dockerfile` take `ARG VERSION`); local builds are `dev`, which disables the check. A client sends `User-Agent: <name>/<version>`, and the backend checks only clients in `clientversion.Known` (currently just cappctl), because other User-Agent versions use unrelated numbering. When a known client is at least one minor release behind the backend, the middleware sets `X-Client-Warning` and increments `capp_backend_outdated_client_requests_total{client,version}` before the chain (so 401/429 responses are covered), then logs `outdated client` after it with `status` and, when the authentication chain supplies a verified username, `user` (`ClusterCredential.ImpersonateUser`; Kubernetes-mode passthrough has only the token, which must never be logged); and cappctl prints that once to stderr. To check another client, declare it in `pkg/clientversion`, add it to `Known`, and have the client send its User-Agent and show the header; the middleware and comparison stay unchanged, and the middleware/server tests loop over `Known`. The metric's `version` label is major.minor, or `vN.x` for an older major, because the User-Agent is caller-controlled and checked before auth; never label it with the raw version. Build CLI clients with `root.State.NewClient`, not `client.New`, so they send the version and print the warning. capp-mcp and shell completion deliberately don't print it.

**AuthManager interface** (`internal/auth/manager.go`): Factory selects implementation based on `auth.mode` config. Each mode implements `Authenticate`, `Login`, `PasswordLogin`, and `Refresh`. Kubernetes-mode passthrough forwards the caller's token; backend-policy passthrough reviews it at each requested target using that target's backend credential, reusing identities only within the request. OpenShift validates at its in-cluster home reviewer with the existing cache; only Kubernetes mode impersonates users on managed clusters. LDAP mode verifies passwords with directory search-and-bind, issues EdDSA access tokens, and verifies them locally without a directory call on resource requests. Authorization mode selects Kubernetes impersonation or backend policy checks. `GET /api/v1/auth/mode` returns the active mode.

**Backend-policy verification and audit contracts:** OpenShift/passthrough identity rejection returns 401 `UNAUTHORIZED`; reviewer failures return sanitized 503 `INTERNAL_ERROR` / `identity verification is unavailable`, distinct from `POLICY_UNAVAILABLE`. Passthrough global discovery reviews every target with at most four concurrent reviews and fails without partial results on any outage. Migration conceals destination verification failures with 403 `POLICY_DENIED`; source verification failures retain their normal mapping. Keep identities and operator authority target-specific. Audits include trusted `authProvider` and `identityAuthority`; `authority` retains its policy/operator meaning. Never log bearer headers, review bodies or raw reviewer errors. Matching names across authorities require operator-confirmed principal equivalence; local fixtures and readiness cannot certify live-population adoption.

**LDAP contracts:** `POST /api/v1/auth/login` accepts `username`/`password` and returns the existing `TokenPair` with an empty `refreshToken` and `Cache-Control: no-store`. Verified LDAPS protects both the search-account connection and the separate target-user bind; complete group resolution is required before issuance. Unknown/ambiguous users and rejected user passwords return 401 / `UNAUTHORIZED` / `invalid credentials`; directory failures return sanitized 503 / `INTERNAL_ERROR` / `directory service unavailable`. Missing/invalid bearer tokens return 401 / `UNAUTHORIZED` / `request is not authenticated`; expired tokens return 401 / `UNAUTHORIZED` / `token has expired`. Raw-token login is unsupported, refresh returns 501 / `NOT_SUPPORTED` without parsing a body, and OAuth routes remain OpenShift-only. Preserve existing-mode behavior and never log credentials, tokens, keys, or raw directory diagnostics.

LDAP clients submit passwords over HTTPS, retain access tokens securely, and log in again on expiry (900 seconds by default). LDAP has no refresh sessions, ADFS SSO, or MFA.

**ClusterManager** (`internal/cluster/manager.go`): Holds connections to all configured clusters, runs health checks every 30s, and creates per-request scoped clients.

**Shared container conversion** (`internal/resources/namespaced/containerspec`, DTOs in `pkg/api/common`): the env-var and CPU/memory conversion that capps and cfunc pools both need lives here once (`EnvVarsToK8s`, `EnvVarsFromK8s`, `MergeEnvVars`, `ParseResourceQuantities`, `ParseCustomResources`, `ResourceSpecFromK8s`), over the `EnvVar`, `EnvVarSource`, `KeySelector`, `ResourceSpec` and `ResourceQuantities` types that `pkg/api/capps` and `pkg/api/cfunc` alias. Put a fix or a new shared container field here, not in one handler's `convert.go`. `EnvVarsToK8s` checks the name of each variable and the name and key of each `secretKeyRef`/`configMapKeyRef` itself, because Gin does not run `binding` tags on the elements of a slice. A variable the DTO cannot express (a `fieldRef` or `resourceFieldRef` set outside the API) is left out by `EnvVarsFromK8s` and carried over by `MergeEnvVars`, which every full-replace env update must call, so a GET response can always be sent back and the variable is not silently deleted; capps and pools both do.

**DTO conversion** (`internal/resources/namespaced/capps/convert.go`): Converts between API request/response types and Kubernetes Capp resources. The DTOs themselves live in `pkg/api/<resource>` packages that import nothing outside `pkg/api` (`capps`, `namespaces`, `configmaps`, `secrets`, `cfunc`, `boundcapps` for the bound-Capps response, `clusters` for `ClusterMeta`, `common` for the types more than one resource uses); the handler packages alias them in their `types.go`, so handler code uses them unqualified. cappctl and capp-mcp import `pkg/api/*` directly, never a handler package: that keeps them at ~250 packages instead of the server's ~1,460 (cold build ~5s vs ~25s). A depguard rule (`light-clients` in `.golangci.yml`) rejects client-go, controller-runtime, Gin, the operator API, `internal/resources` and `internal/cluster` imports in `internal/cli`, `internal/mcpserver`, `cmd/cappctl`, `cmd/mcp` and `pkg/api`. Add new DTO types to `pkg/api/<resource>` plus an alias. `TestConvertCoverage` (`drift_test.go`) fails when a new `CappRequest` field is not populated in `fullCappRequest()` and round-tripped through `ToK8s`/`FromK8s`, so every new field must be wired both ways.

List fields are full-replace on update (`PUT`): `env`, `volumeMounts`, `secretVolumes`, `configMapVolumes`, `nfsVolumes` and `imagePullSecrets` are rebuilt from the request, so omitting one clears it. `imagePullSecrets` (`[]string` of Secret names) maps to the pod spec's `imagePullSecrets`; names are validated as DNS-1123 subdomains and must be unique, but Secret existence/type is not checked (same as env and volume refs).

**Capp log stream** (`internal/resources/namespaced/capps/logs.go`, event DTOs in `pkg/api/capps/logs.go`): `GET .../capps/:name/logs` answers Server-Sent Events, not WebSocket, because the frontend authenticates with an `Authorization` header that neither `EventSource` nor `WebSocket` can send; the UI reads it with `fetch` + `getReader()` and stops it by aborting, so the stream goes through the ordinary middleware chain. Pod watch and log follow are streams the controller-runtime client cannot do: the cluster middleware puts a `cluster.PodStream`, bound to the caller's credential, under `middleware.PodStreamKey` (Kubernetes mode only; the route is `Denied` in backend-policy mode). The Capp is read first (the authz check and the default container: `Containers[0].Name`, else Knative's `user-container`), then the pod watch opens before any byte is written, so a 403/404/400 is still a JSON error; after the headers, failures are `error` events. One goroutine (`logSession.run`) owns all state and the only writer; each followed pod has a reader goroutine that sends `podMsg`s and stops on the session's own cancel, so a client that goes away never leaves a goroutine blocked on a send. The watch starts without a resourceVersion (ADDED for existing pods) and is reopened the same way when the API server closes it or answers 410; pods followed already are skipped. A container is followed once per restart count (`ended`), so a restarted one is followed again from its `StartedAt` (`maxLogTailLines` of history when the status has none); the `ended` entry is dropped when it is, so a later retry of the new container resumes from `lastSeen` instead of being taken for another restart. At most `maxLogStreamPods` (20) at once; a pod over the cap gets one `notice` and starts when a slot frees. Each write sets its own deadline (`logWriteTimeout`, 30 s) instead of `server.writeTimeoutSeconds`, so a client that stops reading ends its stream within 30 s instead of holding it; the route sets `X-Accel-Buffering: no` for nginx, sends a `: keepalive` comment every 15 s, and ends every stream after 30 min with an `end` event. A `pods/log` 403 while the stream runs ends it. Any other failure to open a log, or a log that breaks off with an error, is retried by a timer with backoff (1 s doubling, `maxLogRetries` 5 in a row, then the container is marked ended until it restarts); `retrying` keeps pod events and freed slots from starting it before its timer, and a line resets the count. A retry, `podSinceTime` and `sinceTime` all start the log with `SinceTime`, which the API server rounds down to the second, so `follow` drops the lines not after the last timestamp sent (`lastSeen`) or the one asked for. `podSinceTime` seeds `lastSeen`, so a resumed stream and a retry take the same path; resume is per pod because the lines of different pods do not arrive in time order, so one time for all would skip lines. A clean EOF still means the container stopped. `resources.capps.maxLogStreams` (default 100) caps open streams per instance with a buffered-channel semaphore taken before the Capp read; a stream over it is 503 `LOG_STREAMS_BUSY`. When the rewatch fails, `run` keeps the stopped watch in `podWatch`, because the deferred `Stop` would panic on nil. The Kubernetes-mode user ClusterRole already grants `pods` watch and `pods/log` get; no capp-mcp tool or cappctl command covers it (a stream does not fit an MCP tool call).

**Reload on Secret/ConfigMap change** (`internal/resources/namespaced/boundcapps`): `reloadOnBoundResourceChange` maps to the `rcs.dana.io/rollout-on-bound-resource-change` annotation (omitting it on `PUT` clears it). On every ConfigMap/Secret `PUT`, opted-in Capps that reference it (env, envFrom, volumes, projected volumes, imagePullSecrets) get the resource's `resourceVersion` recorded in the JSON annotation `capp.dana.io/bound-resource-versions` (`{"Secret/db":"123"}`, plus informational `restarted-at`/`restart-reason`), via `Update` with conflict retry. Restarts are keyed on resourceVersion, not a timestamp or a data diff: each change restarts exactly once, even two in the same second, and repeating a PUT whose restarts partly failed (500) restarts only the Capps still behind. An unchanged PUT skips the resource write so its resourceVersion stays put. Those keys must stay outside `rcs.dana.io/`: the operator drops `rcs.dana.io/*` Capp annotations when building the Knative template, so only a non-prefixed key creates a new revision. `DELETE` returns 409 while any Capp references the resource; for Secrets that also covers `logSpec.passwordSecret`, which is bound but never reloaded (the operator, not the pods, reads it).

`routeSpec.rolloutStrategy` is the exception to full replace: omitting it on `PUT` keeps the current strategy, because removing one mid-rollout makes the operator promote the candidate or pin traffic. Only `DELETE .../rollout/strategy` removes it. Stage ordering rules belong to the operator webhook and are not duplicated here.

`containerPort` (`*int32`) is likewise kept when omitted on `PUT`, so clients that predate the field don't reset an app to Knative's default 8080. It maps to the first container's single `ports` entry; changing the number keeps that entry's name (e.g. `h2c`) and protocol. `ToK8s` rejects ports outside 1–65535 and Knative's reserved queue-proxy/profiling ports, because the operator webhook does not check them.

### Configuration

Loaded from YAML file (`--config` flag) + environment variable overrides with `CAPP_` prefix and `_` separators (e.g., `CAPP_AUTH_MODE=openshift`). Priority: env vars > YAML > code defaults.

Default config: `config/config.yaml`. Key settings:
- `authorization.mode`: kubernetes (default) | backend-policy (all three auth modes)
- `authorization.restrictedBindingNamePrefixes`: explicit non-null list required in backend-policy; `[]` means unrestricted prefixes, no Go default
- `clusters[].authorization`: policyNamespace, protectedNamespaces, operatorUsers/operatorGroups; YAML/Helm only, restart all replicas after changes
- `clusters[].allowedNamespaces`: outer boundary for users/operators in both modes; empty adds no name restriction
- `auth.mode`: passthrough | openshift | ldap
- `auth.ldap`: directory URL/CA, search DN/filter/attribute settings, login deadline, token lifetime, issuer/audience, and Ed25519 signing/trust keys; validated only in LDAP mode
- `clusters[]`: array of cluster connections with credentials
- `resources.cfunc`: off by default; `registryPrefix` (default `ghcr.io/fission`, env `CAPP_RESOURCES_CFUNC_REGISTRYPREFIX`), `imagePullSecret`, `allowCustomBuild` (default false), `maxPoolSize` (default 10), `defaultSize`, `sizes` (name → requests/limits) and `flavors` (name → `image`, `buildImage`, `buildCommand`, `builderEnv`, `keepArchive`). When enabled it needs at least one size and one flavor, and `defaultSize` must be a size; startup also rejects a flavor image that is not a valid reference or already names a registry while `registryPrefix` is set, a flavor or size name with a dot (Viper would split it), a negative quantity, and a `buildCommand` without a `buildImage`. The Helm chart ships `sizes: {}` and `flavors: {}` because Helm merges maps, so a default entry could not be removed by an override
- `resources.cfunc.functions`: off by default; `git.baseURL` (https only), `git.token` (env `CAPP_RESOURCES_CFUNC_FUNCTIONS_GIT_TOKEN`, Helm `secret.cfuncGitToken`), `git.username` (default `oauth2`), `maxTriggers` (10), `maxTimeoutSeconds` (300), `defaultConcurrency` (500), `maxConcurrency` (500), `minCronIntervalSeconds` (60). Startup rejects functions without cfunc, a missing or non-https base URL, a missing token (the message never prints it), a limit below 1 and a default above its maximum. `resources.cfunc.onboardNamespaces` (default false) and the per-cluster `clusters[].cfuncRouterURL` (http or https) belong to it
- `resources.<name>.enabled`: feature flags for resource handlers (all on by default)
- `resources.capps.maxLogStreams`: open Capp log streams per instance (default 100, at least 1 when capps is on); each follows up to 20 pod logs
- `resources.observability`: per-Capp metrics endpoints, off by default (`enabled`); when on, requires `queryURL` (a Prometheus-compatible server; inject via `CAPP_RESOURCES_OBSERVABILITY_QUERYURL`) and at least one entry in `metrics`. Each metric's query (or each of its `series`) is parsed as PromQL, and every vector selector (including a bare metric name with no braces) must contain the `$selector` placeholder; `clusterLabel` is required on every metric when more than one cluster is configured, because `queryURL` is shared; with one cluster it is optional and startup logs a warning naming the metrics without it (`MetricsWithoutClusterLabel`), since a Prometheus shared with other backends' clusters would return their same-named Capps too — `resources.observability.labels` adds extra matchers (e.g. to pin a shared Prometheus) to every query
- `cappSizes`: small/medium/large resource presets served at `/api/v1/sizes` and passed to the capps and revisions handlers
- `gitops`: optional Git sync; per-cluster `clusters[].gitOpsPath` nests under `gitops.pathPrefix`
- `server.corsAllowedOrigins`: defaults to `localhost:3000` (capp-frontend dev server)
- `tracing.*` is parsed, but no OTLP exporter is wired up in code

`auth.ldap.url` accepts only `ldaps://` endpoints, with port 636 when omitted. Both directory connections verify certificates and hostnames before sending credentials. `auth.ldap.caCert` supplies a base64 PEM CA bundle; empty uses system roots. StartTLS is unsupported, and `ldap://` URLs fail startup validation.

LDAP passwords and PEM private keys come from `CAPP_AUTH_LDAP_BINDPASSWORD` and `CAPP_AUTH_LDAP_SIGNINGPRIVATEKEY`; Helm supplies them from `secret.ldapBindPassword` and `secret.ldapSigningPrivateKey`. Supply public `auth.ldap.verificationKeys` maps through mounted YAML, not JSON environment variables. Key IDs use lowercase ASCII letters/digits, `-`, and `_`. All replicas need consistent issuer/audience and signing/trust configuration plus synchronized clocks. Distribute a new public key before activating its private key, and retain retiring keys until their tokens expire. Directory account/password/group changes do not revoke issued tokens; removing a signing key fleet-wide invalidates all its tokens after rollout.

Every backend-policy provider requires inline backend tokens for every target; OpenShift and LDAP also require them in Kubernetes mode. Backend-policy passthrough requires HTTPS, a valid base64 PEM CA, `insecure: false`, and no kubeconfig path. Users/groups impersonation permissions apply in Kubernetes authorization mode; backend-policy uses one backend credential and a consolidated ClusterRole/ClusterRoleBinding per target for observation, administration and authorized resource operations. Canonical usernames/groups must match User/Group RoleBindings in Kubernetes mode or application bindings in backend-policy mode; the default LDAP filter resolves direct membership only, without guaranteed nested/primary groups. Keep required Projects access for Kubernetes-mode namespace listing. Backend-policy TokenReview grants belong on the OpenShift home workload account or every passthrough target backend identity; LDAP needs none. Only OpenShift accounts receive OAuth annotations. The chart honors configured service-account names and `create: false` in backend-policy mode. Directory operators own AD lockout policy/recovery, platform operators own distributed gateway controls, and automation must stop on rejected credentials rather than retry. The optional backend rate limiter is per IP and per instance.

### cappctl CLI

Binary at `cmd/cappctl/`. Built with Cobra. No Gin or K8s imports (enforced by depguard) — pure Go + stdlib.

**Command tree:**
```
cappctl login / logout
cappctl context list | use <name> | current
cappctl mcp-headers
cappctl completion bash|zsh|fish|powershell
cappctl get      capps [name] [--bound-to secret/<name>|configmap/<name>]
cappctl create   capps
cappctl update   capps <name>
cappctl delete   capps <name>
cappctl sync     capps <name> [--disable]
cappctl migrate  capps <name>
cappctl rollback capps <name> --to-revision N [-y]
cappctl rollout  capps <name> --action promote|abort|retry [--revision REV] [-y]
cappctl rollout  capps <name> --remove-strategy [-y]
cappctl get      capprevisions --capp <name> [revision]
```

**Global flags:** `--server`, `--token`, `--cluster`, `--namespace`, `--context`, `--output` (table|wide|json|yaml), `--insecure`

**Env var overrides (CI-friendly):** `CAPP_SERVER`, `CAPP_TOKEN`, `CAPP_CLUSTER`, `CAPP_NAMESPACE`

**Config file:** `~/.config/cappctl/config.yaml` (0600, atomic write). Stores named contexts with server URL, auth mode, access token, expiry, cluster, and namespace; OpenShift contexts may also have a refresh token. LDAP login clears previous refresh credentials and never persists the password.

**LDAP login:** `cappctl login --auth-mode ldap` supports `--username` with LDAP-only `--password-stdin`, or `--token` import. Stdin is bounded to 16 KiB raw bytes, validated as UTF-8, and has at most one terminal LF/CRLF removed; other bytes are preserved. Reject empty passwords, `--password` (even empty), and token/password-flag combinations. Explicit/detected non-LDAP modes reject `--password-stdin` before reading input or starting an interactive flow. LDAP login requires verified HTTPS, rejects `--insecure`, never prompts/opens a browser, and rejects all credential-request redirects without saving a context. Imported JWT `exp` must be usable, positive, numeric, and in the future; parsing it without signature verification supplies local metadata only, never authentication.

**Token expiry and refresh:** `PersistentPreRunE` in `internal/cli/root/root.go` checks selected context tokens before authenticated commands. OpenShift contexts with refresh credentials refresh when expiry is at most 30 seconds away. LDAP contexts never refresh or silently reauthenticate: at or after known expiry, return exactly `LDAP access token expired; run cappctl login again` before handler/network execution. Unexpired LDAP tokens remain usable within the last 30 seconds. Preserve flag > environment > context precedence; `--token`/`CAPP_TOKEN` overrides do not inherit expired active/named context metadata, including when using its server. Backend verification still applies to overrides.

**LDAP automation and trust:** Use a dedicated AD account and supply stdin from a secret store, as shown in [docs/cappctl.md](docs/cappctl.md#ldap). Repeat login explicitly on expiry; stop on rejected credentials and rotate stale secrets rather than retrying. Install private backend HTTPS CAs in the trust store of the workstation/container running the CLI. `auth.ldap.caCert` is the backend's directory trust setting, not CLI backend trust. Preserve existing OpenShift password/browser/direct-token and passthrough behavior. Run `make lint` and `make test` after CLI documentation changes as well as code changes.

**MCP integration:** `cappctl mcp-headers` (`internal/cli/auth/headers.go`) prints `{"Authorization": "Bearer <token>"}` after the same root authentication checks as resource commands. Expired LDAP context tokens produce a nonzero exit and no headers; the helper cannot renew them. Explicit login must precede reconnecting after LDAP expiry. OpenShift refresh remains supported. Configure a Claude Code MCP `headersHelper` with `"headersHelper": "cappctl mcp-headers --context <name>"`; see [the CLI reference](docs/cappctl.md#mcp--claude-code).

**Adding a resource:** implement `ResourceCommand` interface (`internal/cli/resource/handler.go`), call `registry.Register` in `cmd/cappctl/main.go`. No other files change. The interface requires `RegisterSyncCommand(parent *cobra.Command)`, `RegisterMigrateCommand(parent *cobra.Command)`, `RegisterRollbackCommand(parent *cobra.Command)` and `RegisterRolloutCommand(parent *cobra.Command)` — implement as no-ops if sync, migrate, rollback or rollout is not applicable to the resource.

### Startup Sequence
1. Load config (YAML + env vars) → validate
2. Init zap logger
3. Build K8s scheme (register CRD types)
4. Create ClusterManager → connect to clusters → start health checks
5. Create GitOps client (if `gitops.enabled`) → clone remote repo
6. Build resource handler registry
7. Call `server.New`: construct the authorization runtime in backend-policy mode → create AuthManager (based on `auth.mode`) using the runtime's clients when available → assemble the Gin server → start namespace/policy observers and UID workers in backend-policy mode
8. Start auth background cleanup (if the auth manager implements it) → listen on :8080
9. Graceful shutdown on SIGTERM/SIGINT (30s drain)
